Case studies/PROTECT

PROTECT: case management for Wisconsin prosecutors

PROTECT (Prosecutor Technology for Case Tracking) is the system District Attorney offices across Wisconsin's 72 counties use to manage cases. For 18 months I was its only designer. I created the brand, redesigned how case details appear in the desktop app, and rebuilt a 2005-era inter-county search tool. The web design system started from IBM's Carbon Figma kit, with light and dark modes.

The problem

A statewide legal system with no brand, no design system, a 2005 search tool and a desktop app that made people switch tabs for every case.

What I did

As the only designer for 18 months: the brand, a web design system built from IBM Carbon with light and dark modes, three web tools, desktop changes in Fluent UI, and 300+ screens made consistent.

Result

Live: three web interfaces (XCQ, eFiling and Administration) built on the new web design system, and the desktop app with the new changes. All tested in QA with the BAs. Plus the new logo and brand files.

Context

One platform, four very different design problems

PROTECT is built by the state's DA IT program (DAIT). It isn't one app. It's a Windows desktop application, a set of web tools, and the documents and training material around them. Each piece had its own users and its own technical limits.

The desktop app follows Microsoft Fluent UI, and I designed with the Telerik and ComponentOne components the developers were building with. Across desktop and web, I moved more than 300 older Windows-based screens into one consistent experience.

I worked directly with business analysts, who knew the legal workflows deeply, and with the developers who would build each piece. There was no other designer, so I owned everything from discovery notes to final specs.

Without a design team, I also led the work around the design: I ran workshops and the bi-weekly design reviews with the BAs and stakeholders, reviewed builds with developers and helped with HTML, CSS and Angular, and mentored teammates on UX and Figma.

Research

Learning a legal domain with limited access to users

Prosecutors and their staff are busy, and government projects don't always grant designers direct sessions with them. I combined what I could get: BA-led requirement sessions, walkthroughs of the live tools, feedback already logged by users, and stakeholder reviews of every prototype. When I couldn't test with end users, I ran proxy sessions where analysts who support DA offices worked through the prototype while I watched and took notes.

Strategic trade-offs

What I gave up, and why it was the right call

Modern patterns vs. the Windows desktop framework

OptionAnimated drawers, hover reveals, flexible layouts
ChosenStatic expand/collapse sections, click and keyboard only

Engineering confirmed the desktop renderer couldn't support animation or reliable hover. I checked every proposed element with a developer before it went into a frame, so nothing had to be cut later.

Show every result vs. paginate

OptionKeep the old “load everything” behavior people knew
ChosenPaginate, with a page-size choice of 10, 25 or 50

Large surname searches were slow in the old tool. Letting people set the page size kept their habit of scanning long lists without the slow load.

Fresh visual style vs. continuity

OptionA new look unrelated to the desktop app
ChosenDerive XCQ from the PROTECT brand: same navy, gold and type

Staff move between desktop and web all day. Shared colors and components make the web tools feel like the same product.

Wait for user access vs. test with proxies

OptionPause decisions until DA staff were available
ChosenProxy sessions with analysts, plus a decision log

Waiting would have stalled the schedule. Proxies caught most usability issues, and the decision log recorded what still needed confirming with real users.

Design system

Built from IBM Carbon, extended for PROTECT

I didn't draw the web design system from scratch. I started from IBM's Carbon Figma kit, kept what already worked for dense, data-heavy tools, and changed what PROTECT needed. Carbon is made for enterprise software, which suited staff who read tables all day.

Tokens

Carbon's roles, PROTECT's colors

Kept Carbon's token roles (background, layer, field, text, border, support) and pointed them at PROTECT navy and gold. Two modes: Light and Dark.

Components & states

From the kit, restyled

Buttons, inputs, notifications and tags from the kit, restyled with PROTECT tokens. Each state is a variant: default, hover, focus, disabled, error and read-only.

Data table

Carbon's table, extended

Carbon's data table as the base. I added surname-first sorting, inline aliases, a page size of 10, 25 or 50, and a last-synced footer.

Grid, spacing & type

One layout system

Carbon's grid, spacing scale and type scale, so XCQ, eFiling and Administration line up and feel like one product.

Keeping the library easy to use
  • Components use semantic tokens only, never raw colors, so switching a frame to Dark changes the whole screen.
  • Properties and variants cover the states designers need, so nobody has to detach an instance.
  • New patterns from product work go back into the library, like the data-freshness banner from eFiling.
  • The decision log records what was approved, by whom and when.
  • One shared Figma library; developers see the same token names in Dev Mode.
Systems & governance

One library, four products

There was no design system when I joined. I started from IBM's Carbon Figma kit and built it out in stages: brand tokens first, then the XCQ component library, then patterns the desktop and eFiling work could share.

The eFiling site search was the test. Its people and case lookup was assembled almost entirely from existing XCQ components. The one new pattern it needed, a banner for data freshness, went back into the library for everyone.

To keep it governed as a solo designer, I kept a decision log in the file. Every approved and pending choice was written down with the date and who approved it, which kept settled decisions from being reopened in reviews.

Outcome & reflection

What went live, and what I'd do differently

I delivered a new logo, a design system for the web, three web interfaces (XCQ, eFiling and Administration) and changes to the desktop app. Engineering built from my Figma specs, everything went through QA testing with the BAs, and all of it is now live.

“What stood out most was Shivani's ability to adapt across a wide range of challenges, from UI/UX for multiple platforms to logos and icons.”
Lisa FangmannBusiness Analyst, Wisconsin

Build the library earlier

The full component library came together months in. Starting with it would have made the later workstreams faster.

Start the decision log on day one

It started as a fix for repeated debates. From the first week, it would have prevented them.

Push for direct user sessions sooner

Proxy testing worked, but a few early sessions with DA staff would have confirmed the desktop and web split weeks earlier.
